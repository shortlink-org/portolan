# Custom properties and local authoring

Status: implemented for services and contexts. Other entity types remain follow-up work.

## Using it

Run `portolan dev`, open a service's Overview tab or a context page, and choose **Add resources or properties**. Select a type, enter a stable `x-*` key and label, inspect the preview, then choose **Save & rebuild**. Existing rows expose **Edit**; the editor also supports removing a property on save. Unsaved drafts are recoverable in the same browser.

The first save enables `annotations: "annotations/<catalog-id>"` on the selected catalog profile in `portolan.json`. A workspace without profiles uses top-level `annotations: "annotations/default"`. Commit that configuration and the authored files together. The property editor writes only into this dedicated workspace directory, including when the entity comes from an external project.

Static builds display the saved properties without an editor. Links support titles, destination hosts, purpose icons, and copy actions. The available types are `link`, `text`, `number`, `boolean`, `tags`, and `json`. Property values are catalog content and are included in the built site.

## Reader and scope

A developer opening a service needs its runbook, dashboard, and organization-specific facts. They should be able to add that information from `portolan dev`, keep it in Git, and see it after extraction and in the published catalog.

The implemented release enriches existing services and contexts. Flows, events, aggregates, stores, and ADRs can follow using the same renderer and an expanded target contract. Creating architectural entities or overriding extracted facts is a separate authoring feature.

## Existing foundations

- `scripts/local-api.mjs` and `src/lib/local-api.ts` provide the local control plane. ADR editing already checks manifest/file revisions, writes atomically, and starts generation.
- `src/pages/AdrCreate.tsx` distinguishes a saved source from successful catalog generation. Reuse that distinction.
- `scripts/catalog-sources.mjs` merges sources, applies the catalog profile, enriches, and validates. Authoring data must enter the shared loading path so generators and the application agree.
- `src/components/DocsLinks.tsx` provides browser-configured Confluence search and Notion workspace links. These are personal integration shortcuts, whereas an authored link belongs to a specific catalog resource and is shared through Git.
- `src/catalog-model.ts` is a validated contract, mirrored in Go and schema tooling. This is not a frontend-only addition.

## Storage and contract

Use separate, explicitly configured authoring files in the catalog workspace. Do not edit generated fragments, fetched snapshots, or external project source trees. This is the supported authoring format:

```json
{
  "version": 1,
  "catalog": "example",
  "target": { "kind": "service", "id": "shop.oms" },
  "properties": {
    "x-runbook": {
      "type": "link",
      "label": "Runbook",
      "group": "Operations",
      "value": {
        "url": "https://docs.example.com/oms/runbook",
        "label": "Order recovery",
        "purpose": "runbook"
      }
    },
    "x-rto": {
      "type": "number",
      "label": "Recovery objective",
      "group": "Operations",
      "unit": "min",
      "value": 30
    },
    "x-data-classification": {
      "type": "tags",
      "label": "Data classification",
      "group": "Governance",
      "value": ["internal", "personal-data"]
    }
  },
  "order": ["x-runbook", "x-rto", "x-data-classification"]
}
```

The location is `annotations/example/service/shop.oms.json`, enabled by `annotations: "annotations/example"` on the example catalog profile. Context files use `annotations/example/context/<id>.json`; IDs are URI-encoded in filenames. Keep these files outside catalog-fragment globs and extractor cleanup. The local API resolves filenames from validated identities; it does not accept arbitrary client file paths. This also permits annotating an external project without writing into it.

Identity is catalog + entity kind + canonical ID, never the display name or route. Nested entities must carry their owning scope when their identifiers are not globally unique. Use an explicit discriminated target union, expanding it only as each entity kind is supported.

Initially each property carries its label, type, and display options. Reserve `x-*` keys for user properties. Once shared organization definitions are needed, introduce reusable definitions with the same value contract; do not start with a mandatory schema-management screen.

Values enter an optional `Catalog.annotations` collection with provenance generated by the loader: authoring source path and `declared` basis. Generated consumers must preserve this collection. No property changes a service's evidence status, ownership, relationships, or deployment state. A custom label named “Status” is not runtime health.

Validate authoring syntax and unique targets/keys; resolve against the complete merged catalog; then retain only annotations belonging to the selected catalog profile. A resource excluded by a profile is not an orphan. A missing target in the full catalog remains preserved in the source file and produces an actionable diagnostic; do not silently reattach it to a similarly named entity. Duplicate assignments from different authoring sources require resolution rather than last-write-wins.

Deleting a property removes only its authored value. Changing a property's type requires a compatible value or explicit replacement. Renaming an entity does not guess a new target: an orphan produces a Problems diagnostic while the source file remains intact. Retarget it by editing its target and moving the file to match. A target picker is follow-up work.

## Reading the page

Place a `Resources` block near the service summary for useful external destinations, followed by grouped `Properties` rows. Keep the existing identity, architectural evidence, tabs, and diagrams primary. Each property appears once: links displayed in Resources are not repeated in Properties.

The first implementation should use one shared section with these two subgroups. Keep it in the main page pane; the existing detail rail serves selected evidence and is not a permanent metadata sidebar.

| Type | Presentation | Editor |
| --- | --- | --- |
| `link` | Icon by purpose, human title, visible host, external-link marker; open and copy URL actions | Title, URL, purpose; `https`/`http` validation |
| `text` | Wrapping text; expanded detail for long content | Text input or textarea |
| `number` | Aligned numeric value and explicit unit | Numeric input and optional unit |
| `boolean` | Explicit Yes / No; not an interactive switch in reading mode | Checkbox with a visible label |
| `tags` | Neutral labels that wrap; no implied navigation | List editor |
| `json` | Collapsed object/array with readable keys, expand and copy | Validated JSON editor as an advanced option |

Links are the first specialized renderer. Dashboard, runbook, documentation, repository, and generic purposes choose icons and vocabulary; they do not fetch previews or imply integration, availability, or live health. Render compact rows by default. Consider tiles only when a destination has its own useful summary, not simply because it is a URL.

Always show `0`, `false`, and empty strings according to their actual meaning. An absent property renders nothing. Empty arrays/objects remain inspectable when explicitly authored. Unsupported future types retain a readable raw fallback with an unsupported-type indication.

Show source provenance once for a shared block, with per-property detail if sources differ. Keep `declared` visually and semantically separate from verified evidence. Property definitions and the source path are available in a disclosure instead of making raw keys dominate the page.

An entity reference deserves a later `reference` type with a catalog entity picker, route-helper navigation, and unresolved-target handling. Do not guess entity identity from arbitrary strings or add graph edges from a metadata reference.

## Editing in dev mode

1. The resource section exposes `Add property` and row-level `Edit` actions only when the local API confirms this catalog is writable. `import.meta.env.DEV` alone is insufficient.
2. `Add property` opens the existing `SidePanel` pattern. Choose type first, then show only relevant fields. Existing values have the same editor.
3. The editor shows a live rendering preview, field validation, save destination, and explicit Save / Discard actions. Source JSON is an optional disclosure. Reuse `Modal`/`SidePanel` focus containment, Escape, and focus return behavior.
4. Save sends the catalog/target identity, manifest revision, and file revision. Server-side validation and path containment checks precede an atomic write. A new file uses an expected-absent revision so concurrent creation cannot overwrite another writer.
5. Display `Saving` → `Saved; rebuilding catalog` → `Catalog updated`. A write failure retains the draft. A rebuild failure says the source is saved and offers `Retry rebuild`; it must not claim the displayed catalog is current or resave the same draft implicitly.
6. A revision conflict retains the draft and offers comparison against the disk version. The user chooses how to resolve it; there is no automatic overwrite.

Drafts may use browser storage keyed by workspace, catalog, target, and base revision. They are not the persisted source of truth. Navigation with unsaved edits uses the established editor protection. Discard restores the editor's base value; deleting a persisted property is a distinct action.

In static/deployed mode, render the same saved content without mutation controls. A resource with no custom properties has no empty reader section; local mode offers a compact `Add resources or properties` entry point. Custom metadata ships with the catalog, so credentials and private tokens are not property values.

## Implementation coverage and acceptance

1. **Storage and read path:** typed contract, manifest schema and Go mirror, explicit manifest directories, merge/profile behavior, provenance, and orphan diagnostics. Old catalogs without annotations remain valid.
2. **Read UI:** shared typed renderer on service/context pages, including groups, empty values, link actions, and source details.
3. **Local authoring:** capability discovery, typed editor, atomic revision-checked write, generation state, retry, draft recovery, and read-only behavior.

Focused checks must cover regeneration preserving authoring files, profile isolation, `false` and `0`, unsafe URL schemes, unknown targets, duplicate properties, concurrent edits, failed generation after a successful write, and external source trees remaining unchanged. A URL string is not executable HTML or a custom component; render text safely and allow only the supported URL schemes.

For implementation verification, run the affected contract/API/component tests and `npm run gen`. Run `npm run likec4:gen` when the change touches diagram inputs or generated diagram presentation. Reload the exact service/context preview with a cache-busting query and inspect the property section and editor; inspect the rendered diagram too if it changed. A JSON snapshot is not rendered UI verification.

Organization-wide property templates, filters/search, bulk editing, richer Markdown, and project-supplied React renderers can follow actual usage. The initial renderer registry should use a closed set of supported types; arbitrary code execution is not part of adding catalog data.

## Reference

[EventCatalog custom properties](https://www.eventcatalog.dev/docs/development/customization/custom-properties) uses `x-*` resource properties, renders nested values, and allows passing values to custom components. Portolan can adopt the extension namespace while providing built-in typed presentation and dev-mode authoring suited to its generated catalog.
